REPOSITORY DECISION RECORDS (RDR)



RDR-001: Monorepo with Domain-Based Structure



Decision: Single monorepo containing all services, shared libraries, infrastructure, AI modules,
and documentation. Domains organized by bounded context from Volumes 11-19.

Why: 60+ microservices require extensive code sharing. Monorepo enables atomic refactoring,
consistent versioning, simplified dependency management, and unified CI/CD. Domain-based
structure maps directly to architecture.

Alternatives: Polyrepo (rejected — coordination overhead for 60+ repos); Hybrid with separate
library repos (rejected — versioning hell with rapid AI development).

Trade-offs: Larger clone size (mitigated by sparse checkout), but significant gains in developer
velocity and consistency.



RDR-002: Go Workspaces + Python Monorepo Tools



Decision: Go workspaces (go.work) for Go services, Pants build system for Python monorepo
management, pnpm workspaces for frontend/Node.js packages.

Why: Each language ecosystem has different monorepo tooling maturity. Go workspaces are
native and stable. Pants provides Python monorepo support at scale. pnpm is the standard for
Node.js monorepos.

Alternatives: Bazel (rejected — too complex for initial phases, may adopt later); Nx (rejected —
JavaScript-centric, Go/Python support limited).

Trade-offs: Three build tools instead of one, but each is best-in-class for its ecosystem.



RDR-003: Contract-First with Centralized API Definitions



Decision: All API definitions (Protobuf, OpenAPI, JSON Schema, AsyncAPI) live in /api/ at
repository root. Code generation produces language-specific clients. Breaking changes detected
in CI.

Why: APIs are the contracts between services. Centralized definitions ensure consistency,
enable parallel development, and provide single source of truth for code generation.

Alternatives: API definitions in each service (rejected — scattered, inconsistent, hard to
discover).

Trade-offs: Requires discipline to update central definitions first, but eliminates integration
surprises.



RDR-004: Template-Based Service Scaffolding



Decision: Every service created from standardized templates using cookiecutter (Python) and
custom Go templates. Templates enforce Clean Architecture, observability, and security
patterns.

Why: 60+ services must be consistent. Templates eliminate boilerplate decisions and ensure
every service follows standards from Volume 21.

Alternatives: Manual service creation (rejected — inconsistent, error-prone at scale).

Trade-offs: Template maintenance overhead, but essential for consistency across 60+ services.

1.2 Monorepo Strategy

```yaml

monorepo_strategy:

 organization: Domain-based with shared infrastructure



 boundaries:

  api/: API contracts (single source of truth)

  services/: Business logic services (by bounded context)

  libs/: Shared libraries (cross-cutting concerns)

  ai/: AI models, prompts, datasets

  infrastructure/: IaC, Kubernetes, Terraform

  docs/: Documentation, ADRs

  tests/: E2E, integration, performance tests

  tools/: Developer tooling, scripts



 dependency_flow:

  direction: |

   services/ ──depends on──         libs/

   services/ ──depends on──         api/ (generated code)

   ai/ ──depends on──       libs/

   infrastructure/ ──independent── (references service images)

   tests/ ──depends on──       services/ (integration tests)



  rule: |

   Services CAN depend on shared libraries

   Services CANNOT depend on other services

       Services communicate ONLY via APIs and events

       Libraries CANNOT depend on services



 ownership:

      model: CODEOWNERS per domain directory

      example: |

       /services/truth-engine/ @agbofa/truth-engine-team

       /services/content-factory/ @agbofa/content-factory-team

       /libs/go/          @agbofa/platform-team

       /infrastructure/     @agbofa/platform-team

```

package events



import (

      "context"

      "encoding/json"

      "fmt"



      "github.com/IBM/sarama"

      "go.opentelemetry.io/otel"

)



// Producer provides standardized Kafka event publishing

type Producer struct {

      client sarama.SyncProducer

      tracer trace.Tracer

      metrics *ProducerMetrics

}



// ProducerConfig configures the event producer

type ProducerConfig struct {

      Brokers     []string

      ClientID    string

    Acks         sarama.RequiredAcks // WaitForAll for critical events

    EnableTracing bool

}



// NewProducer creates a new standardized event producer

func NewProducer(config ProducerConfig) (*Producer, error) {

    saramaConfig := sarama.NewConfig()

    saramaConfig.Producer.RequiredAcks = config.Acks

    saramaConfig.Producer.Return.Successes = true

    saramaConfig.Producer.Idempotent = true

    saramaConfig.Producer.Compression = sarama.CompressionSnappy

    saramaConfig.ClientID = config.ClientID



    client, err := sarama.NewSyncProducer(config.Brokers, saramaConfig)

    if err != nil {

        return nil, fmt.Errorf("create kafka producer: %w", err)

    }



    return &Producer{

        client: client,

        tracer: otel.Tracer("events/producer"),

        metrics: NewProducerMetrics(),

    }, nil

}



// Publish publishes an event to Kafka with tracing and metrics

func (p *Producer) Publish(ctx context.Context, event Event) error {

  ctx, span := p.tracer.Start(ctx, "events.Publish")

  defer span.End()



  // Serialize event

  payload, err := json.Marshal(event)

  if err != nil {

      return fmt.Errorf("marshal event: %w", err)

  }



  // Determine topic from event type

  topic := p.eventTypeToTopic(event.EventType())



  // Build Kafka message

  msg := &sarama.ProducerMessage{

      Topic: topic,

      Key: sarama.StringEncoder(event.EventID()),

      Value: sarama.ByteEncoder(payload),

      Headers: []sarama.RecordHeader{

           {Key: []byte("event_type"), Value: []byte(event.EventType())},

           {Key: []byte("tenant_id"), Value: []byte(event.TenantID())},

      },

  }



  // Inject tracing headers

  otel.GetTextMapPropagator().Inject(ctx, NewKafkaHeaderCarrier(&msg.Headers))

      // Publish

      partition, offset, err := p.client.SendMessage(msg)

      if err != nil {

          p.metrics.RecordError(event.EventType())

          return fmt.Errorf("publish event: %w", err)

      }



      span.SetAttributes(

          attribute.String("kafka.topic", topic),

          attribute.Int64("kafka.partition", int64(partition)),

          attribute.Int64("kafka.offset", offset),

      )



      p.metrics.RecordSuccess(event.EventType())

      return nil

}

"""

LLM Gateway Client — Standardized interface for all LLM interactions.

All services use this client to interact with LLMs. It provides:

- Model routing (cost-optimized tiering)

- Automatic retries with exponential backoff

- Response caching

- Token usage tracking

- Prompt template rendering

"""



from dataclasses import dataclass

from typing import Optional, Any

import structlog



logger = structlog.get_logger(__name__)




@dataclass

class LLMRequest:

  """Standardized LLM request."""

  prompt: str

  model: str = "claude-3-sonnet"

  temperature: float = 0.4

  max_tokens: int = 4000

  response_format: Optional[str] = None # "json" for structured output

  cache_ttl: int = 3600 # Cache duration in seconds

@dataclass

class LLMResponse:

  """Standardized LLM response."""

  text: str

  model: str

  tokens_used: int

  cost_usd: float

  cached: bool = False

  latency_ms: float = 0.0




class LLMClient:

  """

  Standardized LLM client for all Agbofa services.



  Usage:

    client = LLMClient(default_model="claude-3-sonnet")

    response = await client.generate(LLMRequest(

         prompt="Generate a headline for...",

         temperature=0.4,

    ))

  """



  def __init__(self, default_model: str = "claude-3-sonnet"):

    self.default_model = default_model

    self._cache = {} # In-memory cache (use Redis in production)

  self._token_tracker = TokenTracker()



async def generate(self, request: LLMRequest) -> LLMResponse:

  """

  Generate LLM response with automatic retries and caching.

  """

  # Check cache

  if request.cache_ttl > 0:

    cache_key = self._cache_key(request)

    if cache_key in self._cache:

        logger.debug("llm_cache_hit", model=request.model)

        return self._cache[cache_key]



  # Route to appropriate model

  model = request.model or self.default_model



  # Generate with retries

  for attempt in range(3):

    try:

        response = await self._call_llm(model, request)



        # Track token usage

        self._token_tracker.record(response.tokens_used, response.cost_usd)



        # Cache response

        if request.cache_ttl > 0:

          self._cache[cache_key] = response



      logger.info(

          "llm_generated",

          model=model,

          tokens=response.tokens_used,

          cost=response.cost_usd,

          latency_ms=response.latency_ms,

      )



      return response



    except Exception as e:

      logger.warning(

          "llm_retry",

          model=model,

          attempt=attempt + 1,

          error=str(e),

      )

      if attempt == 2:

          raise

      await asyncio.sleep(2 ** attempt)

PART XII — FOUNDATION DECISION RECORDS



```markdown

## RDR-001: Monorepo with Domain-Based Structure

**Decision:** Single monorepo with bounded context organization

**Rationale:** 60+ services, shared code, atomic refactoring

**Trade-offs:** Clone size vs. development velocity



## RDR-002: Go Workspaces + Pants + pnpm

**Decision:** Three build tools, each best-in-class for ecosystem

**Rationale:** Go workspaces native, Pants for Python scale, pnpm standard

**Trade-offs:** Three tools vs. one, but optimal per ecosystem



## RDR-003: Contract-First API Development

**Decision:** Centralized API definitions, code generation

**Rationale:** Single source of truth, parallel development

**Trade-offs:** Upfront API design vs. iteration speed



## RDR-004: Template-Based Service Scaffolding

**Decision:** Cookiecutter templates for all services

**Rationale:** Consistency across 60+ services

**Trade-offs:** Template maintenance vs. consistency gains



## RDR-005: Docker Compose for Local Development

**Decision:** Full local environment via Docker Compose

**Rationale:** Identical dependencies to production

**Trade-offs:** Resource usage vs. environment fidelity



## RDR-006: Trunk-Based Development

**Decision:** Short-lived branches, continuous integration

**Rationale:** Rapid AI-assisted development

**Trade-offs:** Branch discipline vs. merge conflict reduction

```
