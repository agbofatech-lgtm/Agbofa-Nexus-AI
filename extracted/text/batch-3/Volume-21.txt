ARCHITECTURE DECISION RECORDS (ADR)



ADR-ENG-001: Monorepo with Domain-Based Structure



Decision: Single monorepo with domain-based directory structure, shared libraries, and
independent service deployment.

Rationale: 60+ microservices require shared types, protobuf definitions, and utilities. Monorepo
enables atomic changes across services, consistent versioning, and simplified dependency
management.

Alternatives Considered: Polyrepo per service (rejected — coordination overhead too high for
60+ services); hybrid with shared libraries as separate repos (rejected — versioning complexity).

Consequences: Larger clone size, but tooling (Bazel/Nx) mitigates build impact.



ADR-ENG-002: Trunk-Based Development with Short-Lived Feature Branches



Decision: Trunk-based development on main branch. Feature branches live maximum 2 days.
Release branches created for production stabilization only.

Rationale: AI-assisted development generates code rapidly. Long-lived branches create merge
conflicts with AI-generated code. Trunk-based development ensures continuous integration.

Alternatives Considered: GitFlow (rejected — too heavyweight for rapid AI development);
GitHub Flow (adopted with modifications).

Consequences: Requires high test coverage and feature flags for incomplete features.



ADR-ENG-003: AI-First Development Workflow



Decision: AI coding agents are first-class contributors. All AI-generated code must pass same CI
checks as human code. AI pull requests follow identical review process.

Rationale: Platform designed for AI-assisted development. Formalizing AI contribution workflow
ensures quality and auditability.

Consequences: CI must handle higher PR volume; review process must be efficient.



ADR-ENG-004: Contract-First API Development



Decision: All services define APIs in Protobuf/OpenAPI before implementation. API contracts are
reviewed and approved before coding begins.

Rationale: 60+ services require clear contracts. Contract-first prevents integration issues and
enables parallel development.

Consequences: Upfront API design effort, but significant reduction in integration issues.

1.3 Clean Architecture Rules



```yaml

clean_architecture:

 layer_dependencies:

      rule: Dependencies point inward. Outer layers depend on inner layers.



      layers:

       domain:

           description: Enterprise business rules

           dependencies: NONE (pure Go/Python)

           contains: Entities, Value Objects, Domain Services, Repository Interfaces

           rules:

            - No framework imports

            - No database imports

            - No HTTP/gRPC imports

            - Pure business logic only



       application:

           description: Application use cases

           dependencies: domain

           contains: Use Cases, Application Services, DTOs, Ports

   rules:

    - Orchestrates domain objects

    - Implements application-specific logic

    - No infrastructure concerns



  infrastructure:

   description: Technical implementations

   dependencies: domain, application

   contains: Repository implementations, API clients, Message brokers

   rules:

    - Implements interfaces defined in inner layers

    - Contains all framework-specific code

    - Database queries, HTTP clients, etc.



  interfaces:

   description: External APIs

   dependencies: application, infrastructure

   contains: gRPC handlers, HTTP handlers, Event consumers

   rules:

    - Thin layer, delegates to application services

    - Request/Response mapping only

    - Authentication/Authorization enforcement



dependency_injection:

 tool: Uber FX (Go), dependency-injector (Python)

 pattern: Constructor injection

      anti_pattern: Service locator, global state

```



1.4 Twelve-Factor Application Standards



```yaml

twelve_factor_compliance:

 factor_1_codebase:

      rule: One codebase per service, tracked in monorepo

      compliance:      Monorepo with domain-based structure



 factor_2_dependencies:

      rule: Explicitly declare and isolate dependencies

      go: go.mod with version pinning

      python: pyproject.toml with locked dependencies

      container: All dependencies in container image

      anti_pattern: System-level dependencies assumed



 factor_3_config:

      rule: Store config in environment variables

      implementation: |

       # CORRECT

       DB_HOST=${DB_HOST}

       KAFKA_BROKERS=${KAFKA_BROKERS}



       # INCORRECT

  DB_HOST=localhost # Hardcoded

 config_sources:

  - Environment variables (Kubernetes ConfigMap/Secrets)

  - HashiCorp Vault (secrets only)

  - Never: Config files in repository



factor_4_backing_services:

 rule: Treat backing services as attached resources

 implementation: Connection strings from environment

 services: PostgreSQL, Neo4j, MongoDB, Redis, Kafka, S3



factor_5_build_release_run:

 rule: Strictly separate build and run stages

 pipeline: Build → Test → Containerize → Deploy

 immutable: Container images never modified after build



factor_6_processes:

 rule: Execute as stateless processes

 state: All state in backing services (databases, caches)

 sticky_sessions: Never



factor_7_port_binding:

 rule: Export services via port binding

 implementation: Services bind to $PORT environment variable



factor_8_concurrency:

      rule: Scale out via process model

      implementation: Horizontal Pod Autoscaling in Kubernetes



 factor_9_disposability:

      rule: Fast startup, graceful shutdown

      startup_time: <10 seconds

      shutdown: SIGTERM handling, drain connections, finish in-flight requests

      health_checks: Readiness and liveness probes



 factor_10_dev_prod_parity:

      rule: Development, staging, production as similar as possible

      implementation: Same container images, different configs

      gap: Time (fast feedback), personnel (devs can deploy), tools (same stack)



 factor_11_logs:

      rule: Treat logs as event streams

      implementation: stdout/stderr, structured JSON logging

      aggregation: OpenTelemetry → Loki



 factor_12_admin_processes:

      rule: Run admin tasks as one-off processes

      implementation: Kubernetes Jobs, same codebase, same config

```

 format: "DOMAIN-SUBSYSTEM-NUMBER"

  - "TRUTH-VERIFY-001": Claim verification failed

  - "DIST-PUB-002": Platform publishing timeout

  - "COMPLY-COPY-003": Copyright check unavailable



 implementation: |

  type ErrorCode string



  const (

      ErrClaimVerificationFailed ErrorCode = "TRUTH-VERIFY-001"

      ErrSourceTimeout          ErrorCode = "TRUTH-SRC-002"

  )



  type ServiceError struct {

      Code   ErrorCode `json:"code"`

      Message string `json:"message"`

      Cause error      `json:"-"`

      Retryable bool    `json:"retryable"`

            Severity string `json:"severity"`

    }



    func (e *ServiceError) Error() string {

            return fmt.Sprintf("[%s] %s", e.Code, e.Message)

    }



gRPC_error_mapping: |

func MapToGRPC(err error) error {

        var svcErr *ServiceError

        if errors.As(err, &svcErr) {

             switch {

             case svcErr.Code.IsNotFound():

                 return status.Error(codes.NotFound, svcErr.Message)

             case svcErr.Code.IsInvalidArgument():

                 return status.Error(codes.InvalidArgument, svcErr.Message)

             case svcErr.Code.IsUnauthenticated():

                 return status.Error(codes.Unauthenticated, svcErr.Message)

             case svcErr.Code.IsRateLimited():

                 return status.Error(codes.ResourceExhausted, svcErr.Message)

             default:

                 return status.Error(codes.Internal, svcErr.Message)

             }

        }

        return status.Error(codes.Internal, "internal error")

}

13.2 Final Engineering Recommendations



1. Start with Foundation: Deploy infrastructure and foundation services first. Everything
depends on them.

2. Contract-First Development: Define all API contracts before coding. This enables parallel team
work.

3. AI as Accelerator: Use AI coding agents for initial implementation, but always with human
review.

4. Ship Incrementally: Deploy each service as it's ready. Don't wait for the full platform.

5. Monitor from Day One: Don't defer observability. Every service must emit metrics and traces
from the start.

6. Test in Production (Safely): Use canary deployments and feature flags to validate in
production.

7. Document as You Go: Documentation is code. Review it, version it, keep it current.

8. Security is Continuous: Integrate security scanning in CI/CD. Never defer security to a later
phase.

9. Own Your Services: Service teams own development, deployment, and operations.

10. Measure and Improve: Use SLOs to drive decisions. Continuously improve based on data.
