INFRASTRUCTURE DECISION RECORDS (IDR)



IDR-INF-001: Monorepo with Domain-Based Structure



Decision: Single monorepo containing all services, infrastructure, AI modules, and
documentation. Domain-based directory structure matching bounded contexts from Volumes
11-29.

Rationale: 60+ microservices require shared types, protobuf definitions, and utilities. Monorepo
enables atomic refactoring, consistent versioning, and simplified CI/CD.

Alternatives: Polyrepo (rejected — coordination overhead for 60+ repos); hybrid with shared
library repos (rejected — versioning complexity).

Trade-offs: Larger clone size (mitigated by sparse checkout), but significant gains in developer
velocity and consistency.



IDR-INF-002: GitOps with ArgoCD + Flux



Decision: ArgoCD as the primary GitOps tool for application deployments, Flux for infrastructure
reconciliation. All deployments driven by Git state.

Rationale: GitOps provides complete audit trail, automated drift detection, and disaster
recovery through Git. ArgoCD provides excellent UI and multi-cluster management.

Alternatives: Flux-only (rejected — less mature UI); traditional CI/CD push (rejected — lacks
GitOps benefits).

Trade-offs: Requires Git discipline, but provides complete deployment auditability.



IDR-INF-003: Istio Ambient Mesh (Sidecar-Less)



Decision: Istio Ambient Mesh for service-to-service communication, replacing traditional sidecar
proxies with ztunnel (L4) and waypoint proxies (L7).

Rationale: Reduces resource overhead by 40-60% compared to sidecar model. Ambient mesh
provides zero-trust networking without per-pod sidecar injection.

Alternatives: Traditional Istio sidecars (rejected — resource overhead); Linkerd (rejected —
fewer enterprise features); no mesh (rejected — security requirements).

Trade-offs: Requires Kubernetes 1.29+, but significant resource savings.



IDR-INF-004: APISIX as Unified API Gateway



Decision: Apache APISIX as the single API gateway for all north-south traffic, replacing multiple
ingress controllers.

Rationale: APISIX provides dynamic routing, plugin-rich architecture, and superior performance
compared to NGINX-based alternatives. Native etcd integration for configuration.

Alternatives: Kong (rejected — higher resource usage); NGINX Ingress (rejected — limited plugin
ecosystem); Traefik (rejected — fewer enterprise features).

Trade-offs: Learning curve for APISIX-specific configuration, but significant operational benefits.

1.2 Branching & Release Strategy



```yaml

branching_strategy:

 model: Trunk-Based Development



 branches:

      main:

       purpose: Production-ready code

       protection:

        required_reviews: 1

        required_checks: [lint, test, security-scan, build]

        allow_force_push: false



      feature/*:

       purpose: Short-lived feature branches (max 2 days)

       naming: feature/TICKET-123-description

       merge_to: main



      fix/*:

  purpose: Bug fixes

  naming: fix/TICKET-456-description

  merge_to: main



 hotfix/*:

  purpose: Critical production fixes

  naming: hotfix/TICKET-789-description

  merge_to: main (with backport to release branch)



 release/*:

  purpose: Release stabilization (max 2 days)

  naming: release/v1.2.3

  merge_to: main (after release)



versioning:

 strategy: Semantic Versioning (MAJOR.MINOR.PATCH)

 release_cadence:

  PATCH: As needed (hotfixes)

  MINOR: Weekly (every Wednesday)

  MAJOR: Quarterly (planned)



 changelog:

  format: Keep a Changelog

  automation: Generated from conventional commits



 tags:

       format: v{MAJOR}.{MINOR}.{PATCH}

       example: v1.2.3

       signed: true (GPG)

```

```dockerfile

# infrastructure/docker/Dockerfile.go — Multi-stage Go Build

# Stage 1: Build

FROM golang:1.22-alpine AS builder



RUN apk add --no-cache git ca-certificates



WORKDIR /build

COPY go.mod go.sum ./

RUN go mod download



COPY . .

RUN CGO_ENABLED=0 GOOS=linux go build \

      -ldflags="-w -s -X main.version=${VERSION} -X main.commit=${COMMIT}" \

      -o /app/service \

      ./cmd/server



# Stage 2: Runtime

FROM gcr.io/distroless/static-debian12:nonroot



COPY --from=builder /app/service /app/service

COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/



USER nonroot:nonroot

EXPOSE 9090 9091 9092

ENTRYPOINT ["/app/service"]

```

PART XV — ENTERPRISE ADRs



```markdown

## IDR-INF-001: Monorepo with Domain-Based Structure

**Decision:** Single monorepo for all services, infrastructure, and AI modules

**Rationale:** 60+ services require shared code; monorepo enables atomic changes

**Trade-offs:** Larger clone size, mitigated by sparse checkout



## IDR-INF-002: GitOps with ArgoCD

**Decision:** ArgoCD for application deployments, Flux for infrastructure

**Rationale:** Complete audit trail, drift detection, disaster recovery via Git

**Trade-offs:** Git discipline required, but essential for compliance



## IDR-INF-003: Istio Ambient Mesh

**Decision:** Sidecar-less service mesh for zero-trust networking

**Rationale:** 40-60% resource savings vs traditional sidecars

**Trade-offs:** Requires K8s 1.29+, but significant efficiency gains



## IDR-INF-004: APISIX as Unified API Gateway

**Decision:** Apache APISIX for all north-south traffic

**Rationale:** Dynamic routing, plugin-rich, superior performance

**Trade-offs:** Learning curve, but operational benefits justify



## IDR-INF-005: Multi-Region Active-Active

**Decision:** Three-region deployment with global traffic management

**Rationale:** 99.99% availability, data sovereignty, sub-second failover

**Trade-offs:** Higher infrastructure cost, but essential for global news platform



## IDR-INF-006: Trunk-Based Development

**Decision:** Short-lived feature branches, continuous integration to main

**Rationale:** Enables rapid AI-assisted development, reduces merge conflicts

**Trade-offs:** Requires high test coverage and feature flags



## IDR-INF-007: Canary Deployments with Automated Rollback

**Decision:** Progressive canary deployments with metric-based validation

**Rationale:** Reduced blast radius, automated recovery from bad deployments

**Trade-offs:** More complex deployment configuration

```
