ARCHITECTURE DECISION RECORDS (ADR)



ADR-OPS-001: Multi-Region Active-Active Deployment



Decision: Deploy Agbofa Nexus AI across three AWS regions (us-east-1, eu-west-1, ap-southeast-
1) in active-active configuration with global traffic management via Route 53 latency-based
routing.

Rationale: Autonomous newsroom requires 99.99% availability. Multi-region active-active
eliminates single-region failure risk and provides data sovereignty for regional compliance.

Alternatives Considered: Active-passive (rejected — failover latency unacceptable for breaking
news); single-region multi-AZ (rejected — insufficient for global audience).

Consequences: Higher infrastructure cost, data replication complexity, but essential for platform
reliability targets.



ADR-OPS-002: Istio Ambient Mesh for Service Communication



Decision: Use Istio Ambient Mesh (sidecar-less mode) for service-to-service communication,
replacing traditional sidecar proxies.

Rationale: Reduces resource overhead by 40-60% compared to sidecar model. Ambient mesh
provides zero-trust networking without per-pod sidecar injection.

Alternatives Considered: Traditional Istio sidecars (rejected — resource overhead); Linkerd
(rejected — fewer enterprise features); no mesh (rejected — security requirements).

Consequences: Requires Kubernetes 1.29+, newer technology but significant resource savings.



ADR-OPS-003: GitOps with Flux CD



Decision: Use Flux CD for GitOps-based continuous delivery, with all infrastructure and
application configs stored in Git.

Rationale: GitOps provides audit trail, rollback capability, and disaster recovery through Git. Flux
CD is CNCF-graduated with strong Kubernetes integration.

Alternatives Considered: ArgoCD (evaluated — equivalent; Flux chosen for tighter integration
with our Terraform workflow); traditional CI/CD push (rejected — lacks GitOps benefits).

Consequences: Requires Git discipline, but provides complete deployment auditability.



ADR-OPS-004: Tiered Storage with Automatic Data Lifecycle



Decision: Implement automatic data tiering: Kafka (7 days hot) → S3 Standard (90 days warm)
→ S3 Glacier (7 years cold) with automatic lifecycle policies.

Rationale: News platform generates 50TB+ daily. Cost-effective storage requires automatic
tiering based on access patterns and compliance requirements.

Consequences: Complex lifecycle policies, but 60-70% storage cost reduction.

```yaml

# Argo Rollouts Configuration for Canary Deployments

apiVersion: argoproj.io/v1alpha1

kind: Rollout

metadata:

 name: content-factory-service

 namespace: content-factory

spec:

 replicas: 10

 strategy:

      canary:

       # Canary steps

       steps:

        - setWeight: 5   # 5% traffic to canary

        - pause:

          duration: 5m # Wait 5 minutes

        - analysis:

          templates:

           - templateName: error-rate-check

           - templateName: latency-check

 - setWeight: 25 # 25% traffic

 - pause:

   duration: 10m

 - analysis:

   templates:

    - templateName: error-rate-check

 - setWeight: 50 # 50% traffic

 - pause:

   duration: 15m

 - setWeight: 100 # Full rollout



# Auto-promotion/rollback based on analysis

autoPromotionEnabled: true

autoPromotionSeconds: 600



# Anti-affinity for canary pods

antiAffinity:

 requiredDuringSchedulingIgnoredDuringExecution:

  - labelSelector:

    matchExpressions:

      - key: app

       operator: In

       values:

        - content-factory-service

   topologyKey: kubernetes.io/hostname

---

# Analysis Template for Automated Validation

apiVersion: argoproj.io/v1alpha1

kind: AnalysisTemplate

metadata:

 name: error-rate-check

 namespace: content-factory

spec:

 metrics:

  - name: error-rate

      interval: 1m

      count: 5

      successCondition: result[0] < 0.01 # Error rate < 1%

      failureCondition: result[0] >= 0.05 # Error rate >= 5%

      failureLimit: 2

      provider:

       prometheus:

        address: http://prometheus.monitoring.svc.cluster.local:9090

        query: |

         sum(rate(http_requests_total{

          namespace="content-factory",

          status_code=~"5.."

         }[5m])) /

         sum(rate(http_requests_total{

          namespace="content-factory"

         }[5m]))

---

apiVersion: argoproj.io/v1alpha1

kind: AnalysisTemplate

metadata:

 name: latency-check

 namespace: content-factory

spec:

 metrics:

      - name: p99-latency

       interval: 1m

       count: 5

       successCondition: result[0] < 2 # p99 < 2 seconds

       failureCondition: result[0] >= 5 # p99 >= 5 seconds

        prometheus:
```

PART X — ARCHITECTURE DECISION RECORDS



```markdown

## ADR-OPS-001: Multi-Region Active-Active

**Decision:** Three-region active-active deployment

**Rationale:** 99.99% availability, data sovereignty, global audience

**Consequences:** Higher cost, replication complexity



## ADR-OPS-002: Istio Ambient Mesh

**Decision:** Istio Ambient (sidecar-less) for service mesh

**Rationale:** 40-60% resource savings vs sidecar model

**Consequences:** Requires K8s 1.29+, newer technology



## ADR-OPS-003: GitOps with Flux CD

**Decision:** Flux CD for continuous delivery

**Rationale:** GitOps audit trail, disaster recovery, rollback

**Consequences:** Git discipline required



## ADR-OPS-004: Tiered Storage Lifecycle

**Decision:** Automatic data tiering (Kafka → S3 → Glacier)

**Rationale:** 60-70% storage cost reduction

**Consequences:** Complex lifecycle management



## ADR-OPS-005: OpenTelemetry for Observability

**Decision:** OpenTelemetry as single observability framework

**Rationale:** Vendor-neutral, CNCF standard, unified collection

**Consequences:** Migration from existing tools if any



## ADR-OPS-006: SPIFFE/SPIRE for Workload Identity

**Decision:** SPIFFE/SPIRE for service identity in Zero Trust

**Rationale:** Cryptographically verifiable identity, automatic rotation

**Consequences:** Additional infrastructure component



## ADR-OPS-007: Aurora Global Database for PostgreSQL

**Decision:** AWS Aurora Global Database for primary relational store

**Rationale:** <1s replication lag, <60s cross-region failover

**Consequences:** AWS lock-in, but best-in-class for PostgreSQL



## ADR-OPS-008: Canary Deployments with Argo Rollouts

**Decision:** Progressive canary deployments with automated analysis

**Rationale:** Reduced blast radius, automated rollback on metric deviation

**Consequences:** More complex deployment configuration



## ADR-OPS-009: FinOps with Automated Optimization

**Decision:** Implement FinOps framework with automated cost optimization

**Rationale:** AI workloads highly variable; manual optimization insufficient

**Consequences:** Initial setup investment, significant ongoing savings



## ADR-OPS-010: Immutable Infrastructure

**Decision:** All infrastructure changes through Terraform; no manual changes

**Rationale:** Reproducibility, disaster recovery, audit compliance

**Consequences:** Slower emergency changes, but essential for reliability

```
